# 技术说明 · 合并器到底做了什么

> 本文写给"想知道它有没有乱改我东西"的人。所有结论都有实测依据。

---

## 1. 一句话

**修复版 APK = 原版 APK + 4 处替换 + 4 组新增。** 合并器就做这件事。

不是重新实现一遍构建流水线——那需要 apktool、JDK、Android SDK；
而实测证明，**那些工作可以预先做完，合并器只需要"换文件"**。

---

## 2. 实测依据：原版 vs 修复版逐条目对比

把原版 APK 与最新修复版 APK 的每个 zip 条目取 SHA256 对比：

| 条目 | 原版 | 修复版 | 结论 |
| --- | --- | --- | --- |
| `resources.arsc` | `fd285436…` | `fd285436…` | **完全相同** |
| `assets/bundle/`（306 项） | — | — | **逐项相同** |
| `assets/pack/`（412 项） | — | — | **逐项相同** |
| `res/`（76 项） | — | — | **逐项相同** |
| `classes.dex` | `985d4105…` | `27f840e8…` | 变了 |
| `AndroidManifest.xml` | `89859309…` | `66062905…` | 变了 |
| `lib/armeabi/librooneyj.so` | `e0c4b63b…` | `36a4826b…` | 变了 |
| `classes2.dex` | 不存在 | 新增 | 服务器 |
| `assets/kssma-data/` | 不存在 | 新增 12 个 | 配置 |
| `assets/database/` | 不存在 | 新增 6 个 | 数据表 |
| `assets/save/` | 不存在 | 新增 6943 个 | 游戏资源 |

**除这 8 项以外，原版一个字节都没动。** 引擎的第一层资源
（`assets/bundle` 设计图纸 + `assets/pack` 出厂资源）保持原样——这是刻意的，
历史上曾因误删它们导致引擎启动失败。

---

## 3. 八步流程

```
输入： 原版 APK  +  资源包 zip  +  修正数据（artifacts/）

 1. 校验原版 APK            SHA256 白名单（防止版本不匹配）
 2. 校验资源包              条目数与关键路径（防止资源不完整 → 崩溃）
 3. 给 .so 打补丁           ★ 对**用户自己的** .so 现场打 54 个字节级补丁
 4. 替换 classes.dex        ← artifacts/classes-dex/（见 §4）
 5. 替换 AndroidManifest.xml ← artifacts/manifest/
 6. 新增 classes2.dex       ← artifacts/classes2.dex（本地服务器）
 7. 新增 assets/kssma-data、assets/database
 8. 新增 assets/save        ← **从用户资源包解出**（6932 项）
 9. 重新打包（zip，4 字节对齐）+ 签名（v1+v2+v3）

输出：KSSMA-Merged-<版本>.apk + merge-report.json
```

## 4. 关于两个二进制的处理方式（法律与技术的权衡）

### 4.1 `librooneyj.so`：**不分发，现场打补丁**

原版 `.so` 与加了 4 个 native 补丁的版本**长度完全相同**（4,476,928 字节），
差异只有 **426 字节 / 54 个区间**，且：

| 检查项 | 结果 |
| --- | --- |
| ELF 头 / 程序头（前 4096 字节） | **0 字节差异** |
| 差异落点 | 仅 `.rodata`（29 区间）+ `.text`（25 区间） |

因为**不改变任何长度**，所以不会破坏 ELF 里任何偏移引用——这是能安全做字节级补丁的前提。

合并器携带的是一份 **JSON 补丁描述**（约 10 KB），形如：

```json
{
  "format": "kssma-binary-patch/1",
  "from_sha256": "e0c4b63b…",     // 原版 .so 必须等于这个
  "to_sha256":   "36a4826b…",     // 打完必须等于这个
  "size": 4476928,
  "regions": [
    { "offset": 1850280, "before": "d9a8fef7d5f8", "after": "24f2fab900bf" },
    …
  ]
}
```

**它不含任何原版二进制内容**，只有偏移与前后字节。合并器应用时：
1. 核对整个文件 SHA256 == `from_sha256`
2. 逐区间核对 `before` 字节（不匹配立即中止，**绝不硬打**）
3. 写入 `after` 字节
4. 核对结果 SHA256 == `to_sha256`

> 已验证：从原版 `.so` 重放补丁 → 得到 `36a4826b…`，**逐字节一致**。

### 4.2 `classes.dex`：见 §8（待定）

`classes.dex` 的情况不同：原版 401,676 字节 → 修复版 402,168 字节，**长度变了 492 字节**。
因为 4 个 smali 补丁中有"插入指令"（`HttpUtil` 各插 8 条、`WebViewWrapper` 插 5 条），
会给 dex 增加常量与方法体，从而需要重算 dex 头部与偏移表。

**所以它不能用"等长字节补丁"处理。**

## 5. 4 个 smali 补丁做了什么

| 补丁 | 改什么 | 目的 |
| --- | --- | --- |
| `EnterDef` 字段默认值 | 3 个 `SelectUrl*_` 字段 `null` → `http://127.0.0.1:10001/…` | 自动登录路径的兜底地址 |
| `HttpUtil` URL 重写 | `connectPost`/`connectGet` 入口把 `game.ma.mobimon.com.tw:10001` 替换为 `127.0.0.1:10001` | **核心**：让引擎请求打到本机 |
| `WebViewWrapper` URL 重写 | `showWebView` 同样替换 | 公告 WebView 不走 `HttpUtil`，需单独处理 |
| `Debug` 方法体恢复 | 4 个方法（release 版被编译为空体） | 恢复引擎日志（`RJ-java` 标签） |
| `LogoActivity` 注入 | `onCreate` 里插一行 `KssmaBoot.start(ctx)` | 启动本地服务器 |

> **为什么用 URL 重写而不是改 hosts**：无需 root、无需改系统文件、任何设备自包含。
> 也曾在模拟器上试过 hosts 方案，因 `/system` 只读（AVB）而不可行。

---

## 6. 4 个 native 补丁做了什么

`.so` 的 4 个补丁让引擎在收到服务器"业务错误"时**正常弹窗**而不是崩溃/静默。
补丁位置集中在：

- `.text`（25 个区间）：修改若干处函数入口的控制流
- `.rodata`（29 个区间）：追加新代码与数据（原区域为空白区）

---

## 7. 安全设计

| 风险 | 对策 |
| --- | --- |
| 版本不匹配 → 换入不兼容的 dex/so → 崩溃 | **SHA256 白名单**，不匹配直接拒绝并明确报错 |
| 资源不完整 → 引擎对缺图零容忍 → 崩溃 | 校验资源包**条目数与关键路径**（如卡图族） |
| 补丁打错位置 | 每个区间**前置校验原字节**，任一不符立即中止 |
| 打到一半失败 → 半成品 APK | 全程写入临时文件，校验通过后才改名 |
| 内存不足 | 全程流式处理，不整包读入内存 |

## 8. 关于 `classes.dex`：为什么它不能用"现场打补丁"

### 8.1 实质改动极小

用 `dex-probe.py` 比较两个 dex 的表结构：

| | 字符串 | 类型 | 原型 | 字段 | 方法 | 类 |
| --- | --- | --- | --- | --- | --- | --- |
| 原版 | 4902 | 684 | 753 | 1335 | 3001 | 334 |
| 修正 | **4909** | **685** | 753 | 1335 | **3002** | 334 |
| 差 | **+7** | +1 | 0 | 0 | +1 | 0 |

**全部实质改动**（字符串池层面）：

| 新增 | 用途 |
| --- | --- |
| `127.0.0.1:10001` | URL 重写目标 |
| `http://127.0.0.1:10001/`、`…/connect/app/`、`…/billing` | `EnterDef` 三个字段默认值 |
| `http://127.0.0.1:50005/`、`…/add_user.php`、`…/world_list.php` | 域名补丁（`dlc.game-CBT.ma.sdo.com` → `127.0.0.1`） |
| `Lkssma/boot/KssmaBoot;` | 启动钩子目标类 |
| `game.ma.mobimon.com.tw:10001` | URL 重写的匹配源 |
| `" \| "` | 引擎日志格式串 |

| 移除 | 原因 |
| --- | --- |
| `http://dlc.game-CBT.ma.sdo.com:50005/`（及 `add_user.php` / `world_list.php` 两条） | 被替换为 `127.0.0.1:50005` 版本 |

### 8.2 但字节级补丁在**原理上**做不到

- 文件长度变了：`401,676` → `402,168`（**+492 字节**）
- 字符串池 +7 条 → `string_ids` 表增大 → **data 区整体后移**
- dex 内部有大量"相对文件开头"的偏移（`map_off`、各表 offset、`code_off`…），全部需要重算
- 实测字节差异：**344,619 字节 / 85.8% / 37,213 个区间**

那 85.8% 主要是**全局偏移 fixup**，不是语义改动。但正因为它们遍布全文件，
**无法用"偏移 + 原字节 + 新字节"的等长补丁表达**。

> 对比：`.so` 和 `AndroidManifest.xml` 都是**等长**修改（`.so` 0 字节变化、
> manifest 两侧都是 5684 字节），所以可以用字节补丁。`classes.dex` 不行。

### 8.3 两个选项（**待你定案**）

| | A. 分发"dex 补丁数据" | B. 分发成品 `classes.dex` |
| --- | --- | --- |
| 做法 | 分发约 1–2 KB 数据（7 条新字符串、1 个新类型/方法、4 个 Debug 方法体、`HttpUtil`/`WebViewWrapper` 的插入指令），合并器对用户 dex 做**真正的 DEX 手术** | 直接分发打好补丁的 dex（402 KB） |
| 法律 | **不分发任何原版二进制**（最干净） | 等于分发原版 dex 的修改版 |
| 风险 | **高**：需要实现字符串池重排 + 全表偏移重算 + 方法体改写；dex 一旦写坏，客户端直接崩 | **低**：已实测可用 |
| 工作量 | 约 2–3 天（且需要大量回归验证） | 约 1 小时 |
| 一致性 | 需要额外证明"手术结果逐字节等于官方 dex" | 天然一致 |

> **我的建议：B**。理由：本案其它部分（Q6 的 `.so`、Q7 的 manifest）已经做到"不分发原版二进制"，
> dex 这一处若强行做 A，会引入**全案最高的崩溃风险**，而收益只是"更干净一点"。
> `classes2.dex`（我们自己的服务器）无论如何都要分发，所以"分发我方 dex"这个前提已经存在。
>
> **备选折中**：A 的简化版 —— 若未来想走 A，可先只在 dex 里**追加字符串与表项**、
> 把方法体注入做成"改写已有方法"（不新增方法），难度会显著下降。但这需要重新设计补丁方式。

## 9. 为什么输出会与"官方修复版"略有不同

合并器产物的**每个条目内容**与官方修复版一致，但以下元数据可能不同：

- zip 条目顺序 / 压缩参数
- 条目的修改时间戳
- 签名（合并器用自签名）
- `merge-report.json` 会记录全部条目哈希，便于你逐条核对

> 本项目的一致性目标是**内容等价**（每个条目的字节相同），不是"整个 zip 逐字节相同"。
> 后者需要固定时间戳与压缩参数，对使用者没有额外价值。

## 10. 性能：为什么它比你想的快

修复版 APK 有 **7763 个条目，其中 7759 个是 STORED（未压缩）**：

| 分组 | 项数 | 原始 | 压缩后 |
| --- | --- | --- | --- |
| `assets/save/` | 6943 | 495.4 MB | 495.4 MB |
| `assets/pack/`（原版） | 412 | 277.5 MB | 277.5 MB |
| `assets/kssma-data/` | 12 | 101.8 MB | 101.8 MB |
| 其它原版 | 78 | 18.4 MB | 18.4 MB |
| `assets/bundle/`（原版） | 306 | 5.6 MB | 5.6 MB |
| 替换项（dex + manifest） | 2 | 0.4 MB | 0.4 MB |
| `META-INF/`（签名） | 3 | 1.4 MB | 0.4 MB |
| `assets/database/` | 6 | 0.3 MB | 0.3 MB |
| `classes2.dex` | 1 | 0.2 MB | 0.2 MB |

**结论**：合并过程不需要重新压缩任何大文件，是纯粹的**条目复制**。
只需要真正压缩 2 个小项（替换后的 `classes.dex` 是 DEFLATED）。

因此：

- **耗时 ≈ 磁盘 IO 时间**（读 773 MB + 写 900 MB），机械盘约 60 秒，SSD 约 20 秒
- **内存占用很低**，可以逐条目流式处理
- 原版的压缩选择**原样保留**，不与官方产物产生差异

> 注：`lib/armeabi/librooneyj.so` 在原版里是 DEFLATED（4.28 MB → 1.80 MB）。
> 合并器打完补丁后需要**按同样方式重新压缩**，这是唯一会消耗 CPU 的大文件。
