## 1. 项目是什么

### 1.1 目标

让 **2013 年国服 KSSMA 安卓客户端**在**没有官方服务器**的情况下完整离线可玩。

### 1.2 客户端

| 项 | 值 |
| --- | --- |
| 包名 | `com.square_enix.million_cn` |
| 原版 APK | `com.square_enix.million_cn-1.0.0.100.0712.M330.apk` |
| 架构 | 32 位 `armeabi`（ARM32 + Thumb-2） |
| 核心 native 库 | `librooneyj.so`（4,476,928 字节，ELF32/ARM/小端） |
| 网络 | HTTP + XML，AES-128-ECB + Base64 |

### 1.3 做法（一句话）

**apktool 反编译原版 APK → 注入自写 Java HTTP 服务器 + 完整资源包 → 重打包签名。**
服务器在设备本机监听，客户端被改指向 `127.0.0.1`。

### 1.4 为什么不分发

编译出的**完全体 APK 内含原版全部资源与剧情**，属于私有可用、**不可公开分发**。
（曾设想做"合并器"让用户自备原版 APK + 资源包，用户决定先不做。）

## 2. 总体架构

### 2.1 分层

```
┌─────────────────────────────────────────────────────────────┐
│ 客户端 APK（反编译 + 重打包）                                  │
│   ├─ classes.dex   原客户端 Java 层（被 patch：域名/校验）      │

┌─────────────────────────────────────────────────────────────┐
```

### 2.5 构建产物与流程

`build/Build-Apk.ps1`（7 步）：

```

[2/7] decode cache reused     apktool 反编译缓存复用
[3/7] patch domains           客户端域名/校验 patch
[4/7] inject boot hook        Application 钩子注入
[4.5/7] swap in accepted librooneyj.so baseline   换入已验证的 native baseline
[5/7] apktool build           重打包 base.apk
[6/7] inject classes2.dex + assets   注入服务器 + 资源（含卡图门禁）
[7/7] zipalign + sign         对齐 + 签名
```

**构建内建门禁**：卡图资源检查（若引用的卡图缺失则构建失败并自动补种）。

## 3. 协议契约（最重要的一章）

> 这一章的每一条都是踩过坑得来的。违反任何一条都会导致客户端**静默失败**（无提示、无反应）。

### 3.1 加密

| 常量 | 值 | 用途 |
| --- | --- | --- |
| **K2** | `rBwj1MIAivVN222b` | **网络协议**：所有 `/connect/app/*` 应答 + 请求参数 |
| K1 | `A1dPUcrvur2CRQyl` | 资源文件（本服务器 v1 不需要，常量备档） |
| ADD_USER_KEY | `B1dACcrvur2YULyl` | `add_user.php` 的 `data_str.password` |

算法：**AES-128-ECB + PKCS5/7 padding**，密文再 **Base64**。

### 3.2 铁律：`/connect/app/*` 的应答**必须加密**

**明文应答会导致客户端 `connectPost:ERROR`**（表现为"什么都没发生"，很难查）。

历史上多次违反此规则：

| 位置 | 症状 | 修正 |
| --- | --- | --- |
| 早期兜底路由 | 客户端只打 `connectPost:ERROR` | 全部改为 `sealed()` |
| 登录失败提示 | 无法提示"密码错误" | 改为加密业务错误 |
| 妖精战 BC 不足 | 返回 HTTP 409 明文 | M11 修正为加密业务错误 |
| 充值路由 | 无路由 → 空信封 → 点了没反应 | M13 改为加密业务错误 |

**业务错误的正规形式**（会触发客户端原生弹窗）：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<response>
  <header>
    <error><code>1</code><message>中文提示</message></error>
  </header>
  <body></body>
</response>
```

### 3.3 请求/应答外形

**请求**：`POST /connect/app/<path>`，参数以 `key=AES_BASE64(值)` 形式放在 form body；
会话靠 Cookie `kssma_session`。

**应答**：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<response>
  <header>
    <error><code>0</code></error>
    <session_id>…</session_id>
    [<command>…</command>]            <!-- 场景驻留等用 -->
    <your_data>…</your_data>          <!-- 见 §3.4 -->
    <next_scene>NNNN</next_scene>     <!-- 决定客户端切到哪个场景 -->
```


### 3.6 AP/BC 回复语义（Gauge）

照 Go 参考（MuMu 实机全功能验收）的 `Gauge`：

> **`current` 是 `lastUpdate` 时刻的值**；服务器与客户端都按 `interval` 秒回 1 点，上限 `max`。

结算时必须**同时推进 `current` 与锚点**（`anchor += gained * interval`），
否则每次请求都会把不足一个 interval 的零头吃掉，**回复比标称速率慢**。

存档字段：`resources.<ap|bc>.{current, max, regenSeconds, lastRegenAt}`，
`lastRegenAt` 单位**秒**（Unix epoch），`null/0` 视为"现在"。
AP 默认 180 秒/点，BC 默认 60 秒/点。

**收口点**：`PlayerSave.settleGauges()`，在 `KssmaServer.loadSave()` 调用
→ 所有 20+ 处读档自动获益，幂等。

### 3.7 其他铁律

| 规则 | 原因 |
| --- | --- |
| 每个动作的 XML 字段**宁多勿缺** | 客户端多处**不做判空**，缺字段会拿到 null 对象 → native 崩溃 |
| 卡牌引用的 `masterCardId` **必须在 master_card 里存在且有立绘** | 否则客户端解析卡面拿到空对象 → 崩溃 |
| `data_type != 1` 的卡**不能发给玩家** | 那是 NPC 卡（161–170），只有占位替身图 |
| 列表类响应**必须带外层包裹节点** | 客户端解析器按固定标签取子元素 |
| 战斗动作 `damage` **不得超过敌方剩余 HP** | 客户端按此绘制血条 |
| `serialId` **永不复用**（高水位 `serialWatermark`） | 合成/进化会删卡，`max+1` 回落可能撞上客户端仍持有的旧 serial |

## 6. 客户端 native 层勘明结论

### 6.1 客户端**不做**伤害计算

关键结论：`<battle_action_list>` 里的 `damage` 是客户端**画出来**的，不是它算的。

证据：客户端有 `_BattleDamageManager`、`BattleImageControler::loadCriticalDamageImage`、
`btl_skill_*.png` 图标，但**没有**伤害计算公式的调用链。

→ **所有战斗数值（含技能/必杀/连携）都由服务端决定**，客户端只负责演出。

### 6.2 客户端支持技能 / 必杀 / 连携的全部字段

| 字段 | 客户端支持 |
| --- | --- |
| `skill_id` / `skill_type` / `skill_card` / `skill_hp_player` | ✅（`_BattleSkillManager`） |
| `combo_id` / `combo_name` / `combo_type` / `combo_card_list_player` / `combo_hp_player` / `combo_ex_player` | ✅ |
| `special_attack_id` / `special_attack_damage` | ✅ |
| `attack_ex` | ✅ |
| `attack_damage` | ⚠️ **未在字符串表中单独找到** |

### 6.3 XML 标签的取证方法（写给未来）

**教训**：这些 TagParser **不含硬编码 XML 标签**（三个都验证过：对战记录 / 妖精奖励 / 合成表）。
它们靠"父元素遍历 + 共享 TiXml 助手"取值 → **从 parser 反汇编里拿不到报文结构**。

这是本项目最重要的方法论结论之一（M17 得出，推翻了我 M11/M16 的原计划）。

**那标签名从哪来？** 从 `.so` 的字符串池里找，并看**同族并列关系**：

```
attacker_history   ← 已确认是"妖精攻击者列表"的 XML 标签（实机显示正常）
fairy_history      ← 报文根标签（实机显示正常）
battle_history     ← 与上面两个并列 → 也是 XML 标签
```

⚠️ 反面教训：`battle_history` 同时是**动画名**（`ae_battle_history.anm`）、
**菜单名**（`menu_battle_history`）和 **XML 标签**。我曾在 M17 因"6 次出现都是动画名"
错误结论它"可能不是标签"——**只因没看全部出现位置**。

### 6.4 字符串归属的判断方法

`.so` 的 `.rodata` 里，**动画/控件名字符串是按类聚集的**。相邻字符串**不一定同属一个类**：

```
… _MenuBattleHistory, 'revenge', 'b_history_list', 'no_revenge', 'on_revenge',
   _goodlistTagParser, _MenuGoodList, 'button_check', **'battles'**, 'all_undisable', …
```

`battles` 属于**留言板 `_MenuGoodList`**，不是对战记录！
（我 M14 据此做了两次错误的报文改动，M16 才发现。）

→ **判断归属必须先找类的边界**（下一个 `_XxxTagParser` / `_Xxx` 类名就是边界）。

### 6.5 `.so` 的指令流是**半字交换**存放的

**现象**：capstone 直接喂文件必然错位。

| | 字节 |
| --- | --- |
| 规范 Thumb-2 `push {r4-r11,lr}` | `e9 2d 4f f0` |
| 文件中实际存放 | **`f0 4f 2d e9`** |

**解法**：把整个文件按 **2 字节半字交换**后，用 `CS_MODE_THUMB` 解码 → 立刻正常：

```
交换后 Thumb @0x2f1631 → mov r8,lr | mov r7,fp | mov r6,sl | mov r5,sb | push {r2,r6} | ldr r1,[pc,#0x3c0]
```

**可靠性已量化**（统计编译器不会生成的可疑指令占比）：

| 函数 | 指令数 | 可疑 | 占比 |
| --- | --- | --- | --- |
| `_GachaCompSheetTagParser::parse` | 202 | 14 | **7%** |
| `_BattleHistoryTagParser::parse` | 51 | 2 | **4%** |
| `_FairyRewardsTagParser::parse` | 179 | 6 | **3%** |

（"可疑"多是合法的 `adds r1,r0,#0` = `add r1,sp,#0`，故**可信**。）

**陷阱**：ARM 模式在**未交换**的文件上会"偶尔碰对"（把真实 Thumb 指令解成看似合理的东西），
容易被误当成正确解码。

### 6.6 `.rel.dyn` 重定位

`.rel.dyn` 197,400 字节 = **24,675 条**重定位。已实现解析（`tools/apply-relocs.py`）。

**结论**：找不到「tag → parser 注册表」的裸指针表——PIC 下是**紧凑的相对偏移结构**，
静态扫不出来，需要**模拟器（unicorn）或重定位后的完整反汇编图**。

### 6.7 客户端行为的实机事实（只有真机能测出）

| 事实 | 细节 |
| --- | --- |
| **`area_id` 语义随路由不同** | `exploration/explore`、`get_floor` 里是 **routeAreaId**（如 5）；`exploration/boss_floor` 里是**区域号**（如 0） |
| 客户端**不会主动请求** `exploration/boss_floor` | 在无守护者配置时（配置未落地），它把守护者层当普通层发 `explore` |
| `battle/battle` 是**对战的**入口 | 守护者战走 `exploration/battle`，不是 `battle/battle` |
| 客户端**不发请求**的情况 | 教程"服务器选择"页列表（来源未识别）；扭蛋合成表入口 |
| 模式选择页 | `tutorial.step >= 0` 时客户端进「开始游戏」模式选择（继续游戏 / 注册账号） |
| 玩家情报页 | 对战流程会用 `{kind=4, user_id=…}` 请求**对手**资料 |
| 妖精讨伐入口 | 在**探索主界面的妖精窗口**，不在菜单的"妖精选择"页（后者只有"全部领取/返回"） |
| `shouldEncounter` | 已有存活妖精时**正确跳过**新遭遇（同一时间只能挂一个） |
| 游戏自绘输入框 | `adb input text` **进不去**（问候语弹窗等），获焦与 `input text` 均无效 |

**构建流程的关键约束**：

- **分发红线**：完全体 APK 不公开分发；keystore/存档不入任何仓库。

**Windows / 沙箱 / 模拟器**：

- Windows `Files.move` 必须带 `REPLACE_EXISTING`；pwsh `Select-Object -Last N` 会缓冲全部输出；

### 9b.2 M21 · 教程 bug **根因（指令级）与修复** ✅

#### 崩溃栈（Houdini 翻译层）

```
F libc : Fatal signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0x0
#01 pc 0038f8e5  librooneyj.so (rooney::res::exists(String)+24)
#02 pc 001c3ae5  librooneyj.so (_Main::connect(smart_ptr<_TXmlParser>)+2060)
#03 pc 0018057b  librooneyj.so (_Main::main(bool)+390)
#04 pc 001aff19  librooneyj.so (Java_com_test_GLRenderer_nativeMain+20)
```

#### 定位方法（可复用）

1. **扫 BL 指令找调用点**：`tools/find-calls.py` 手写 Thumb-2 BL 位域解码
   （capstone 在本 `.so` 上输出乱码，不可用），在 `_Main::connect`
   （0x1C32D8，5752 字节）里扫出 331 条调用，命中崩溃点：

   ```
   +2034  0x1C3ACA -> _TutorialModel::getScriptName()
   +2054  0x1C3ADE -> String::String(const String&)
   +2060  0x1C3AE4 -> rooney::res::exists(String)     ← 💥
   ```

2. **扫成员偏移找赋值点**：`this+0x44`（`_TutorialModel::script_name`）在全库
   **只有一个写入点**：

   ```
   _TutorialModel::next()  @0x1EACDB (+50):
       str r1, [r4, #0x44]
   ```

3. **手工解码 16 位 Thumb 半字**确认 `getScriptName()` 是个 thunk：

   ```asm
   0x1EA73C  B510   push {r4, lr}
   0x1EA73E  1C04   mov  r4, r0
   0x1EA740  3144   adds r0, #0x44      ; this + 0x44
   0x1EA742  F190 FEDB  bl 0x1EA729     ; 调带参重载
   0x1EA746  1C20   mov  r0, r4
   0x1EA748  BD10   pop  {r4, pc}
   ```

#### 根因

> **`script_name` 只在收到 `tutorial/next` 应答时才被赋值**（唯一写入点在上面）。
> 而 `_Main::connect` 在处理**登录应答**时就要取它 → 此时它还是空的 →
> `res::exists` 解引用空指针 → `fault addr 0x0`。
>
> **为什么之前发了 `<tutorial>` 就崩**：发了它，客户端就进入"教程进行中"状态，
> 于是登录应答的处理路径也会去查脚本名。

#### 修复

**登录应答必须发完整主城应答（带 `revision`/`your_data`/`body`），
但 `next_scene` 指向 300，且绝不注入 `<tutorial>` 块。**


### 9b.3 M22 · 合成器（Merger）与 v2/v3 签名

#### 合成器做了什么

用户给**原版 APK + 资源包 zip**，合成器复现全部修复，产出与当前修复版等价的 APK。

| 组件 | 说明 |
| --- | --- |
| `zipio.py` | ZIP **流式重建**：保留原条目顺序、**复用原压缩流**、STORED 条目 4 字节对齐 |
| `apkbuild.py` | 替换 `classes.dex`、注入 `classes2.dex`、`assets/kssma-data`、`assets/database`、`seeds/`、资源包内容 |
| `patch.py` | 字节补丁（`.so` 与 `AndroidManifest.xml` **原地打补丁**，不分发改好的二进制） |
| `sign.py` / `signv2.py` | v1（JAR）+ v2/v3（APK Signing Block） |
| `validate.py` | 白名单校验（原版 APK / 资源包 SHA256、必需子目录、条目数下限） |
| `main.py` | CLI：`--apk --res --out [--artifacts --hi-op --no-sign --report --quiet]` |

**合并结果与参考版对比**：7758 条目完全相同、0 不同、0 仅新增、2 仅参考
（`assets/save/appdata/save_appdata`、`save_version`，**故意跳过**——2014 年的全零
appdata 会让客户端删掉 `save/database/master_card`）。

**压缩方式**：输出 STORED 7757 / DEFLATED 1（参考版只有 `AndroidManifest.xml` 是
DEFLATED）。早期用 `zipfile` 默认压缩导致 5069 个条目变成 DEFLATED，体积和参考版
不一致，已用 `method_for()` 归一。

#### ★ 构建脚本必须同步 `merger/artifacts/`

**踩过的坑**：`Build-Apk.ps1` 只把 `classes2.dex` 装进 APK，
**不会更新 `merger/artifacts/`**。于是合成器会用**旧的 dex** 打出
"看上去正常但缺最新修复"的包。

已在 `Build-Apk.ps1` 的第 1 步之后加入同步（`synced classes2.dex -> merger/artifacts`
/ `kssma-data` / `database`），并用"故意写坏 artifacts 再构建"验证它能自愈。

#### v2/v3（APK Signing Block）实现状态：**结构正确，但未通过 `apksigner` 验证**

**已做对的部分**：

| 项 | 状态 |
| --- | --- |
| 块布局 `u64 size_of_block / u64 size_of_pairs / pairs / u64 size_of_pairs / u64 size_of_block / "APK Sig Block 42"` | ✅ 自洽（`size_of_block = size_of_pairs + 24`，`块长 = 8 + size_of_block + 16`） |
| 4 字节对齐 | ✅ 块长与块首均 `% 4 == 0` |
| pair id | ✅ `0x7109871a`(v2) / `0xf05368c0`(v3) 可被解析器解出 |
| 内容摘要 | ✅ 按 1 MiB 分块（`0xa5` + u32 长度，末块记 0）复算，与块内记录一致 |
| 签名 | ✅ RSA PKCS#1 v1.5 + SHA-256，可用块内公钥验证 |
| v1 | ✅ `apksigner` 报 v1 = true |

**未通过**：`apksigner verify --min-sdk-version 24` 仍报
`Verified using v2 scheme: false` / `v3 scheme: false`，且不打印具体原因。

**踩过的坑（都已修正）**：

| 坑 | 现象 | 修法 |
| --- | --- | --- |
| 块尾漏写 `size_of_block` | 块不被识别 | 块尾是**三个**字段：`sop`、`sob`、magic |
| `size_of_block` 公式错 | 同上 | 最终确认 `size_of_block = size_of_pairs + 24` |
| RSA 公钥 DER 是 **294 B（2 mod 4）** | 块长 2 mod 4，CD 失去对齐 | 末尾追加一个**未识别 id 的 pad pair**（验证器会跳过未知 id） |
| `__pycache__` 缓存 | **连续 3 轮在跑旧代码**，误判公式反复"不生效" | 改完 `signv2.py` 必须清 `__pycache__` |

**对交付无影响**：本 APK **未声明 `targetSdkVersion`**（只有 `minSdkVersion=8`），
Android 11+ 的 v2+ 强制检查不适用 → **MuMu 12 / Android 12 接受 v1-only**。
且 `Build-Apk.ps1` 用 `apksigner.bat sign`，**主 dist 包本来就是 v1+v2+v3 齐全的**。
缺 v2/v3 的只是合成器自己那条 Python 签名路径，故 `main.py` 里
**默认 `wants_v2=False`**（未验证通过前不默认开启）。

**下一步正确做法**（别再猜公式）：用 `apksigner` 签一个 1 KB 的小 APK，
把它的 Signing Block 与我们的**逐字节 diff**，重点看
① 摘要分块算法 ② EOCD 的 `cd_off` 字段是否置 0 ③ v2 signed data 的字段顺序。

| 函数 | 含义 | 打包后 |
| --- | --- | --- |
| `app_dir()` | **可写**目录 | exe 所在目录 → `keystore/` 写这里 |
| `bundle_dir()` | **只读**资源目录 | `sys._MEIPASS` = `_internal/` |
| `find_artifacts()` | 修正数据目录 | 按下面顺序找 |

`find_artifacts()` 顺序（**找到第一个就用**）：

1. 环境变量 `KSSMA_ARTIFACTS`
2. `app_dir()/artifacts` ← **exe 同级**，故意优先于内置，便于用户覆盖
3. `bundle_dir()/artifacts` ← 打包内置，正常走这条
4. 源码树 `../artifacts`

**为什么 `keystore` 必须写 `app_dir` 而不是 `_MEIPASS`**：
`_MEIPASS` 是每次启动新建的临时目录，写进去下次就没了 →
**每次运行签名密钥都会变**，用户装的包会签名冲突。

**自检**：GUI 与 CLI 都有 `--selftest`。CLI 那份（`main.run_selftest`）是唯一实现，
GUI 那份复用它、只额外验证 tkinter 能真开窗——避免两套逻辑再次漂移。

打包后实测（`frozen=True`）：

```
app_dir    : …\KSSMA-Merger
bundle_dir : …\KSSMA-Merger\_internal
artifacts  : …\KSSMA-Merger\_internal\artifacts（存在，71 个文件）   ← CLI 也能找到
结果：✅ 环境就绪
```

覆盖机制实测：移走内置 `artifacts/` → 自检报「不存在」并打印**期望路径**；
设置 `KSSMA_ARTIFACTS` → 立即生效。

**行尾**：新增 `.gitattributes`，仓库内统一 LF（`*.ps1` 保持 CRLF），
避免 Windows/Linux 之间反复产生"整文件改动"。


#### 打包后 exe 的写入限制（已实机确认，2026-10 用户复现）

**现象**：用户在 GUI 里把输出目录设成 `…\workspace\kssma`，合并开始后失败：

```
❌ 失败：[Errno 13] Permission denied:
   'D:/MyFlie/AI/zcode/workspace/kssma\KSSMA-Offline-20261004-1826.apk'
Traceback (most recent call last):
  File "gui.py", line 235, in _run
  File "merger\apkbuild.py", line 106, in merge
  File "merger\zipio.py", line 263, in __init__
PermissionError: [Errno 13] Permission denied: …apk
```

即 `ApkWriter.__init__` 里的 `open(out_path, "wb")` 被拒。

**排查过程**（排除法 + 对照实验）：

| 检查 | 结果 |
| --- | --- |
| 该目录是否存在、是否为目录 | ✅ 存在且是目录，`mode=777` |
| 有无同名残留文件 / 目录占用 | ❌ 无 |
| 该目录能否写小文件 | ✅ 能 |
| 该目录能否写 900 MB | ✅ **能**（Python 写成功） |
| 磁盘剩余空间 | ✅ 74 GB |
| Defender 受控文件夹访问 | 关闭（`EnableControlledFolderAccess=0`） |
| exe 数字签名 / MotW | 未签名 / 无 |

**对照实验**（同一个 exe，只改输出目录）：

| 输出目录 | exe 结果 | Python 结果 |
| --- | --- | --- |
| `build\` | ❌ 1 秒 `Permission denied` | ✅ |
| 用户主目录 | ❌ 1 秒 | ✅ |
| `%TEMP%` | ❌ 1 秒 | ✅ |
| **exe 自身所在文件夹** | ✅ **6 秒写完 799.8 MB** | ✅ |

**结论（经三轮用户实测修正）**：

> 安全软件限制本程序**只能在"程序所在位置那一带的目录树"里写文件**。
> 起初误判为"非程序目录一律被拦"，用户的第三个实验纠正了它。

**用户实验记录**：

| # | exe 位置 | 输出位置 | 结果 |
| --- | --- | --- | --- |
| 1 | 原 `apk` 文件夹 | 同一文件夹 | ✅ 成功 |
| 2 | **复制到别处** | **复制后的新位置** | ✅ 成功 |
| 3 | 原位置 | `D:\Engine`（**其它盘**） | ❌ `Permission denied` |

实验 2 是关键：换位置后能在**新位置**正常输出 → 起作用的不是"输出目录能不能写"，
而是"**exe 在哪一带**"。

**开发的对照实验**（同一 exe，只改输出目录）：

| 输出位置 | 结果 |
| --- | --- |
| exe 文件夹内（默认 `output/`） | ✅ 5 秒写完 799.8 MB |
| exe 文件夹内的子目录 `deep/a/b` | ✅ 5 秒 |
| **exe 的上级目录** | ✅ 5 秒 |
| 完全无关的目录 | ❌ 1 秒 `Permission denied` |

→ 边界是 **exe 的上级目录这棵树**，不是 exe 文件夹本身。

**排除项**：同一目录用 Python 写 900 MB 成功（`D:\Engine` 实测 `makedirs`、
写小文件、写 900 MB 全部 OK）→ 排除权限、磁盘空间、路径形态。
Defender 受控文件夹访问为关闭状态、exe 未签名且无 MotW。

**对用户的实际结论**：**把整个 `KSSMA-Merger` 文件夹放到想输出的地方再运行**；
默认输出目录（程序文件夹下的 `output/`）必然可写。想换位置输出 →
**搬程序文件夹**，而不是改输出目录。

**应对（已落到代码）**：

1. **默认输出目录改为「程序所在文件夹下的 `output/`」**——实测可写的位置。
   若程序目录不可写（如装在 `Program Files`），退回用户主目录
   （`gui.App._prefill` 会先写探针文件判断）
2. **开始合并前预检输出目录**（`gui.App._check_out_dir`）：
   - 路径其实是文件 → 明确说"这不是目录"
   - 建目录失败 → 列出常见原因 + 给推荐路径
   - 写探针文件失败 → 指向「勒索软件防护 / 受控文件夹访问」，
     并给出**动态探测过的**可写路径（`App._suggest_out()`，不写死某个目录）
   - 剩余空间 < 1.1 GB → 提前提示
3. `_run` 里把 `PermissionError` 单独归类，文案改成可执行建议而非原始异常
3b. **报错后主动提议切换**：`_start()` 检测到"目录正常但本程序写不进去"时，
   弹「要不要切到实测可写的目录？」，选「是」则自动填好输出目录并提示
   再点一次「开始合并」——用户不必自己去别处找可写目录
4. README 新增 FAQ，附上上面的实测对照表

**另修一个相关问题**：打包入口是 `gui.py`，而它的 `main()` 原先只判断
`--selftest`，于是 `KSSMA-Merger.exe --apk … --res … --out …` 会
**静默忽略参数、直接开 GUI 干等**（观察到"跑很久然后什么都没发生"）。
现在 `gui.main()` 见到 `--apk/--res/--out/--hi-op/--no-sign/…` 就转 CLI，
实测由"挂起 233 秒无产出"变为 **0.3 秒返回**。

#### frida 在 MuMu 上的可用配置（踩了很多坑才通）

| 障碍 | 解法 |
| --- | --- |
| MuMu 是 x86_64 设备，但应用跑 **32 位**（`app_process32` + `oat/x86`） | 必须用 **x86（32 位）** 版 `frida-server`；x86_64 版看不到该进程 |
| frida 枚举不到 Houdini 翻译的 ARM 库 | 改从 `/proc/<pid>/maps` 读基址 |
| **各段映射到互不相关的地址**（非常规 `base+vaddr`） | 按 ELF `PT_LOAD` 段逐一换算 |
| `dlopen` 在 Houdini 下返回 0 | 不用返回值，直接读 maps |
| toybox 无 `nohup`/`setsid` | 用持久后台作业 + `start_new_session=True` |
| frida 17 API 变更 | `Module.findExportByName` 已不是函数，用 `Process.getModuleByName().findExportByName()` |
| **ARM 层 hook 不可能** | 进程内存里**搜不到任何 ARM 字节**——Houdini 是即时翻译成 x86 |

## 10. 踩过的坑与教训（按主题分类）

### 10.1 Windows / 沙箱

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| `SetNamedSecurityInfoW failed (Win32 5)` | **所有 pwsh 命令被拒** | 用 `diagnose-windows-sandbox-acl` 修复根目录 + `work/`；后续会话切到 danger-full-access |
| PowerShell 5.1 的 `-replace`/here-string 行为 | 补丁未匹配上（`未匹配`） | 用 `edit` 工具做精确替换，别用 `-replace` 拼长字符串 |
| `sed -i` 在 Android 上不可靠 | 改设备配置未生效、grep 正则报错 | 拉回本地用 Python 改 JSON 再推回去 |
| `java -Dfile.encoding=UTF-8` 被 shell 拆坏 | `ClassNotFoundException: /encoding=UTF-8` | 让 Java 程序**直接写 UTF-8 文件**，不靠 stdout |

### 10.2 资产 / 配置 / 启动链（**最贵的一类**）

**根因**：`KssmaBoot.copyAssetDir` 是**幂等跳过**（文件已存在就不覆盖）
→ **老装机永远读旧配置**。

同一个坑**复发三次**：

| 时间 | 受害文件 | 后果 |
| --- | --- | --- |
| M9f | `gacha.json` | 480 卡新池没落地 |
| M9c | `save_appdata` | 卡表模型为空 |
| **M11** | **`exploration.json`** | **守护者 `bossId` 没落地 → 守护者层失效、区域解锁不了** |

**最终修法（治本）**：`KssmaBoot.forceCopyServerConfigs`——
把 `kssma-data` 下**全部 11 个 JSON/XML 配置**逐文件强制覆盖（`op.mp4` 除外）。

> 依据：服务端只写 `kssma-save/` 与 `kssma-data` **之外**的 `fairy-raids.json`，
> 所以 `kssma-data/**` 全是配置、可安全覆盖。
>
> **教训**：只修一个文件是治标；**整类文件收口**才了结。

**其他启动链的坑**：

| 坑 | 现象 | 修法 |
| --- | --- | --- |
| 资源释放与登录竞态 | 引擎在登录后才启动，但资源还没就绪 | `BootGate`：扣住登录应答直到资源就绪（超时 180 秒） |
| `save` 资源标记门 | 老装机 marker 在场 → 跳过 `assets/save` 全量提取 → 补种的文件不生效 | 卡图补种必须用 `forceCopyAssetFile` |
| 缺卡图导致 native abort | 8/8 崩溃栈都是 `thumbnail_chara_168` 缺失 → `JResourceLoader` 抛异常 → native 未判空 | 4 族卡图逐张强制补齐；构建期加资源门禁 |

### 10.3 协议 / 加密

| 坑 | 现象 | 修法 |
| --- | --- | --- |
| 明文应答 | 客户端只打 `connectPost:ERROR`，界面上"什么都没发生" | 一律 `sealed()`；业务错误用 `error code=1 + message` |
| 业务错误也当异常 | 无提示 | 余额不足/BC 不足等都回**业务错误**而非 HTTP 4xx |
| 列表缺包裹节点 | 解析器拿到空对象 | 每个列表补外层节点（如战斗历史 `battles` 那次教训） |

### 10.4 数据 / 存档

| 坑 | 现象 | 修法 |
| --- | --- | --- |
| 二进制表解析错位 | 后续字段全错 | 强制"精确消费到边界"，否则抛异常 |
| 卡牌引用不存在的 master | 客户端解析卡面空对象 → 崩溃 | 发卡/守护者选型时过滤 `data_type!=1` 与卡表缺失 |
| 存档键名不一致 | 剧情进度写进去读不出（`scenario` vs `stories`） | 修模板 + `PlayerSave.migrate()` 兼容老档 |
| "默认值"与"迁移"混在一个函数 | 新账号被改成"已完成"，或老账号被扔回教程 | **需要外部信息（是否新账号）的默认值必须由调用方传入** |
| `serialId` 复用 | 撞上客户端仍持有的旧 serial | 高水位 `serialWatermark` |
| 图鉴字段从没人写 | 卖卡后图鉴记录永久丢失 | `Album`：发卡即记入 + 读档回填 |

### 10.5 adb / 模拟器 / 坐标（详见 §13）

| 坑 | 现象 | 修法 |
| --- | --- | --- |
| `input tap` 坐标系 | 用 `wm size`（1080×1920）点不准 | 必须用 **landscape 1920×1080 逻辑坐标**（来自 `dumpsys window` 的 `mAppBounds`） |
| 截图缩放换算 | 1280×720 截图上的坐标**要 ×1.5** 才是输入坐标 | 我在这上面错了两次 |
| GL 渲染按钮 | `uiautomator` **看不到** | 只能靠截图 + 坐标 |
| 菜单按钮坐标 | 反复点不中 | 见 §13 的实测坐标表 |
| `adb push` 存档后属主 | 文件属 `shell`，应用可能写不回去 | `adb root` 后 `chown 10044:1078` + `chmod 660` |
| 妖精讨伐入口 | 菜单"妖精选择"页找不到战斗按钮 | 入口在**探索主界面的妖精窗口** |

### 10.6 测试方法学

| 坑 | 现象 | 修法 |
| --- | --- | --- |
| 断言依赖精确数值 | 加入随机化后 3 条断言立刻失败 | 改为**不变量断言** + 定种子可复现 + 蒙特卡洛统计 |
| 测试账号复用 | 固定账号名第二次运行已有存档 → "新账号"分支测不到 | 用 `System.nanoTime()` 造唯一账号名 |
| 提取字段没限定块 | 从应答里取 `<name>` 取到 `your_data` 里的**自己** | 取字段必须先定位到目标块（如 `<user_list>`）内 |
| 必杀可达性靠运气测 | 40 场 0 次必杀，断言恒失败 | 用**配置驱动**验证（`ex_gauge_per_turn = 上限` → 必发） |
| 自检 base 存档只有 1 张卡 | 战斗 1~2 回合结束，技能采样窗口太窄 | 平衡评测要用多卡卡组或放大样本 |

## 12. 测试与自检

### 12.1 自检是什么

`server-java/selfcheck/SelfCheck.java` —— 一个**进程内起真实服务器 + 真实 HTTP 请求**的验收脚本。

```
build.ps1 → javac → 起服务器 → 跑 315 条断言 → 输出 passed/failed
```

### 12.2 断言分层

| 层 | 例子 |
| --- | --- |
| 单元级 | 二进制表解析（记录数/精确消费）、卡牌数值公式、名字校验 |
| 协议级 | 每个路由的应答**必须是加密的**、结构含必需字段 |
| 行为级 | BC 扣减、金币/经验结算、区域解锁、图鉴不回退 |
| 不变量 | 战斗 HP 不越界、不会双方同时为 0、回合数合理 |
| 确定性 | 固定随机种子 → 战斗过程完全复现 |
| 统计 | 蒙特卡洛 200 场胜率 ≥ 50%、技能发动次数达标 |
| 配置驱动 | `skill_pct=0` 必须禁用技能；`ex_gauge_per_turn=上限` 必发必杀 |

### 12.3 当前基线

**315 条断言全绿**。

**自检条数的演进**（只增不减，是本项目最重要的纪律）：

| 里程碑 | 断言数 |
| --- | --- |
| M1 | 51 |
| M3 | 55 |
| M5 | 84 |
| M6 | 98 |
| M7 | 149 |
| M8 | 171 |
| M9b | 172 → 173 |
| M9d | 205 |
| M9f | 208 |

| M11 | 248 → 253 |
| M12 | 267 |
| M13 | 281 |

| M16 | 309 |

### 12.4 纪律

> **每次改动都必须跑自检；新增功能必须配断言。**
> 断言失败优先怀疑代码，不要先改断言——但**若断言本身依赖了不该依赖的精确值**
> （如随机化后的伤害），那要改断言为不变量。

三条与自检配套的硬约束：

1. **自检基线只增不减**，每加一个系统先在 `SelfCheck` 追加用例再实现
2. **先确认编译生效再怀疑断言**（javac `-classpath` 曾传错导致静默跑旧 class）
3. **自检要跑在数据副本上**（`work-selfcheck-gmdata`），不污染仓库数据

## 15. 纪律与约定

### 15.1 工作流

1. **先勘明，再动手**：优先找 Go 参考 / 实机日志 / `.so` 字符串，不要凭直觉写
2. **协议优先**：任何新路由都要问"客户端期望什么结构"，不是"我想返回什么"
3. **每次改动都跑自检**，新功能必配断言
4. **实机验证才算完成**：桌面自检只能证明"我的实现自洽"，证明不了"客户端认这个契约"
5. **实机验证前先备份存档**，结束后还原
6. **不留脏状态**：临时改过的设备配置要改回（如把 `skill_pct` 从 100 改回 30）

### 15.2 存档处理约定

- 测试前：`pull` 原档到 `work/save-BACKUP-*.json`
- 测试中：可用注入存档构造场景（如 `tools/prep-boss-test.py`）
- 测试后：**还原并核对签名字段**（region 进度 / 金币 / 持卡数 / 图鉴 / tutorial step）

### 15.3 注释约定（代码里）

- 每个"为什么这么做"都要写清**依据**（哪次实机、哪个参考、哪个坑）
- 历史 bug 的修法要写明**原症状**，防止后人改回去
- 参数**全部可配**放 `runtime-config.json`，避免以后改平衡要重新编译
