# KSSMA Merger · 方案（v1 草案，待确认）

> **目的**：做一个 **PC 端合并器**。用户提供两个文件（原版 APK + 资源包 zip），
> 合并器把所有修正打成一个新的 APK，**功能与当前修复版完全一致**。
>
> **状态**：草案。带 ❓ 的地方需要你拍板（见 §12）。
> **本文档基于实测**，不是设想——所有结论都标注了验证方式。

---

## 1. 结论先行：合并器**不需要**重新实现补丁流水线

这是本方案最重要的一条，它把工作量从"重做整套构建链"降到"换文件 + 补资源"。

实测对比（原版 APK vs 最新修复版 `KSSMA-SelfHost-20261004-1246.apk`，逐条目 SHA256）：

| 条目 | 原版 | 修复版 | 是否变化 |
| --- | --- | --- | --- |
| `resources.arsc` | `fd285436…` | `fd285436…` | **完全相同** |
| `assets/bundle/`（306 项） | — | — | **逐项相同** |
| `assets/pack/`（412 项） | — | — | **逐项相同** |
| `res/`（76 项） | — | — | **逐项相同** |
| `classes.dex` | `985d4105…` | `27f840e8…` | 变了（4 个 smali 补丁 + 启动钩子） |
| `AndroidManifest.xml` | `89859309…` | `66062905…` | 变了（apktool 重编码 + GM 组件改名） |
| `lib/armeabi/librooneyj.so` | 同长度 | `e410d845…` | 变了（原生补丁 + rarity7 详情面板修复） |
| **新增** | — | — | `classes2.dex`（服务器）、`assets/kssma-data`（12）、`assets/database`（6）、`assets/save`（6943） |

也就是说，**修复版 = 原版 + 4 处替换 + 4 组新增**。没有别的东西。

### 1.1 为什么可以"预制成品"而不必现场打补丁

当前流水线里有 4 个 smali 补丁（`patch/*.ps1`），它们都是**对固定文件的固定修改**：

| 补丁 | 改什么 |
| --- | --- |
| `apply-enterdef-defaults.ps1` | `EnterDef.smali` 的 3 个 `SelectUrl*_` 字段默认值 → `http://127.0.0.1:10001/…` |
| `apply-url-rewrite.ps1` | `HttpUtil.smali` 的 `connectPost`/`connectGet` 各插 8 条指令（`.locals` +2），把 `game.ma.mobimon.com.tw:10001` 替换成 `127.0.0.1:10001` |
| `apply-webview-rewrite.ps1` | `WebViewWrapper.smali` 的 `showWebView` 插 5 条指令（`.locals` 7→9） |
| `apply-debug-logging.ps1` | `Debug.smali` 4 个方法补方法体（恢复引擎日志） |
| （构建脚本内） | `LogoActivity.smali` 注入 `KssmaBoot.start(ctx)` 一行 |

**验证**：连续三次交付包的 `classes.dex` **字节级完全相同**
（402,168 字节，SHA256 `27f840e812d29fa6`）。

→ 只要原版 APK 不变，**补丁结果逐字节确定**，可以直接作为成品分发给合并器，
合并器只做"把这个 `classes.dex` 换进去"。

### 1.2 因此合并器的真实职责

```
输入：  原版 APK  +  资源包 zip  +  合并器自带的 artifacts/
处理：
  1. 校验原版 APK（SHA256 白名单 + 存在性检查）—— 防版本不匹配
  2. 替换 classes.dex          ← artifacts/classes.dex
  3. 替换 AndroidManifest.xml  ← artifacts/AndroidManifest.xml
  4. 替换 lib/armeabi/librooneyj.so ← artifacts/librooneyj.so
  5. 新增 classes2.dex         ← artifacts/classes2.dex（服务器）
  6. 新增 assets/kssma-data/   ← artifacts/kssma-data/（12 个配置，含 OP）
  7. 新增 assets/database/     ← artifacts/database/（6 张表）
  8. 新增 assets/save/         ← **从用户资源包 zip 解出**（6943 项）
  9. 重新打包（zip）+ 签名
输出：  KSSMA-Merged-<版本>.apk  +  校验信息
```

**步骤 8 是用户资源包的唯一用途**——它提供 `assets/save/` 全量资源（含卡图、立绘、场景、音效）。
资源包内部结构已确认：`sdcard/Android/data/com.square_enix.million_cn/files/save/…`（6916 项）。

## 2. 技术选型建议

### 2.1 依赖：**纯 Python，零外部工具**（推荐）

关键判断：**合并器不需要 apktool，不需要 javac/d8，不需要 Android SDK。**

| 原流水线依赖 | 合并器是否需要 | 原因 |
| --- | --- | --- |
| `apktool.jar` | ❌ 不需要 | 不做 decode/rebuild；直接换 `classes.dex` 与 `AndroidManifest.xml` |
| JDK / `javac` / `d8` | ❌ 不需要 | 服务器已是成品 `classes2.dex` |
| `android.jar` | ❌ 不需要 | 同上 |
| `zipalign.exe` | ⚠️ 见 §2.3 | 可用 Python 保证对齐（stored 条目 4 字节对齐） |
| `apksigner` | ⚠️ 见 §2.4 | 可用 Python 自行签名 |
| Python + `zipfile` | ✅ 需要 | 处理 APK/资源包 zip |

**收益**：用户只需一个可执行文件（或一份 Python），**不装 Java、不装 SDK、不联网**。

### 2.2 语言：Python 3（+ 可选打包成单文件 exe）

- 现有工具链已经是 Python（`tools/*.py`），可复用大量逻辑与经验
- `zipfile` 足以处理 APK 与资源包（APK 就是 zip）
- 打包成 exe 用 PyInstaller → 用户**双击即可**，无需装 Python

> ❓ 见 §12 Q3：你更想要"单文件 exe"（我推荐）还是"需要装 Python 的脚本"？

### 2.3 zip 对齐（zipalign）

Android 要求未压缩（STORED）条目按 4 字节对齐。Python `zipfile` **不保证**这一点。

**方案**：自己写 zip writer（不改用 `zipfile` 写、而用 `zipfile` 读），逐条目计算
local header 偏移并插入 padding，确保 STORED 条目 data 起始偏移 % 4 == 0。
这是几十行代码，且**可控**（现有流水线里 `zipalign -p 4` 做的就是这件事）。

### 2.4 签名：v1 可纯 Python 实现，v2/v3 需要额外工作

| 方案 | 需要什么 | 兼容性 |
| --- | --- | --- |
| **仅 v1（JAR 签名）** | 纯 Python（`hashlib` + `cryptography` 或手写 RSA） | `minSdk=8` 起即支持；Android 11+ 仍接受 v1。**风险**：Android 14+ 对 targetSdk≥30 才强制 v2+，本应用 **无 targetSdk（默认 8）**，理论上仍接受 v1，但**必须实机验证** |
| v1 + v2/v3 | 需构造 APK Signing Block（v2/v3 格式），可纯 Python 但要写不少代码 | 与现代 Android 一致（当前修复版就是 v1+v2+v3） |

**建议**：**先做 v1，然后实机验证**（装到 MuMu + 真机各一次）。
若 v1 被拒 → 再补 v2（仍然纯 Python，只是多写 ~200 行）。
> ❓ 见 §12 Q4。

### 2.5 是否需要保留原版签名

原版 APK **已签名**（`META-INF/GAMEPLUS.RSA/.SF/MANIFEST.MF`，盛大 GamePlus 签名）。
我们必须**移除原签名并用自己的签名**（否则装不上、也会被视为篡改）。

→ `META-INF/` 下的原签名文件全部删除，写入我们自己的。

## 4. 用户侧流程（目标是"尽量少麻烦"）

### 4.1 理想体验（单文件 exe）

```
1. 下载 KSSMA-Merger.exe（+ artifacts.zip，或首次运行自动下载）
2. 双击 → 出现一个窗口：
     [原版 APK]      [浏览…]
     [资源包 zip]    [浏览…]
     [输出目录]      [浏览…]
     [ 开始合并 ]    （进度条 + 日志区）
3. 完成 → 显示输出 APK 路径、大小、SHA256、以及"下一步：用 adb 安装"
```

### 4.2 无 GUI 时的 CLI（也保留）

```
KSSMA-Merger.exe --apk <原版.apk> --res <资源包.zip> --out <目录>
                 [--artifacts <目录>] [--keystore <自己的.jks>] [--quiet]
```

### 4.3 减少麻烦的具体措施

| 措施 | 说明 |
| --- | --- |
| **零外部依赖** | 不装 Java / SDK / apktool；不联网（除首次取 artifacts） |
| **拖拽支持** | GUI 支持把两个文件直接拖进窗口 |
| **自动识别** | 按文件名/内容识别哪个是 APK、哪个是资源包，用户可只给一个目录 |
| **前置校验 + 人话报错** | 校验 APK SHA256；不匹配时明确说"你提供的 APK 不是本项目支持的那个版本"（而不是抛异常） |
| **进度可见** | 8 个步骤各有进度（`assets/save` 6932 项是主要耗时） |
| **自动签名** | 内置自签名 keystore（首次运行生成并保存在配置目录），用户不需要懂签名 |
| **输出校验** | 打印 SHA256 与大小，便于核对 |
| **一键安装（可选）** | 检测到 adb 时提供"直接装到设备"按钮 |
| **中文界面 + 英文回退** | 面向中文用户 |

### 4.4 预期耗时与体积

| 项 | 值 |
| --- | --- |
| 合并耗时 | 约 **1–3 分钟**（主要是 500 MB 资源的再压缩） |
| 峰值磁盘 | 约 **1.5 GB**（输入 773 MB + 输出 900 MB） |
| 输出 APK | 约 **900 MB**（与当前修复版一致） |
| 内存 | < 500 MB（流式处理，不整包读入内存） |

> 因为输出 APK 是 **900 MB**，得提醒用户：**别用浏览器/FAT32 U 盘传**（FAT32 单文件上限 4 GB 但如果用 7z 分卷要注意）；
> 且安装需要设备**至少 2 GB 空闲**。

## 5. 输出一致性（"保证达成修复版的一切"）

### 5.1 两种保证级别

| 级别 | 含义 | 代价 |
| --- | --- | --- |
| **A. 内容等价**（推荐） | 最终 APK 的**每个条目内容**与修复版一致（仅 zip 元数据/签名不同） | 容易做到，验证简单 |
| **B. 逐字节等价** | 连 zip 顺序、时间戳、压缩参数都一致 → SHA256 完全相同 | 需要固定 mtime、排序、压缩级别；v1 签名含时间戳需固定 |

**建议做 A，并额外提供"条目级校验"**：合并器输出一份 `merge-report.json`，
列出所有条目的 SHA256；提供 `--verify <官方apk>` 让用户自查是否与官方修复版一致。

> ❓ 见 §12 Q5：你要不要挑战 B（逐字节可复现）？技术上可行，但签名时间戳与 zip 元数据要全固定。

### 5.2 我怎么验证合并器真的对

**四层验证**（缺一不可）：

1. **条目级对比**：用原版+资源包跑合并器 → 与官方修复版逐条目比 SHA256
   （预期：除签名相关外**全部一致**）
2. **自检**：合并产物装上设备后跑现有的桌面自检？——不行，自检需要源码。
   → 改为：**装到 MuMu 后跑一份"实机验收清单"**（见下）
3. **实机验收清单**（复现修复版的所有已验收点）：
   - 启动进主城（无崩溃）
   - 探索：进入 region0，楼层与守护者可达
   - 扭蛋：抽卡演出 + 结果页
   - 合成/进化：正常
   - 商店：买 AP/BC 药成功
   - 妖精战：遭遇 → 战斗 → 结算
   - 区域守护者：遭遇 → BOSS 战 → 胜利 → region1 解锁
   - 人机对战：因子页 → 对手列表 → 战斗 → YOU WIN
   - 玩家情报 + 问候语编辑
   - 排行榜
   - 妖精战斗历史
   - 新手教程（新账号）
   - AP/BC 随时间回复
4. **两条路径一致性**：合并器产物 vs 我用原流水线构建的产物，**功能应完全一致**；
   建议保留一次"双产物对拍"作为发布前门槛。

## 7. 许可证与法律

### 7.1 建议：**代码 MIT，第三方工具/素材不进仓库**

| 内容 | 建议许可 | 理由 |
| --- | --- | --- |
| **合并器源码**（`src/`、`scripts/`、`docs/`） | **MIT** | 最宽松、最省事、GitHub 上最常见；与"工具本身无害"的定位匹配 |
| （备选） | Apache-2.0 | 多了专利授权与 NOTICE 要求，本项目无专利诉求 |
| **artifacts/**（我方自制的 dex/so/配置） | 不进 git，Release 分发并在 README 声明 | 体积大；且**`.so` 是原版二进制二次修改产物**，法律属性不同于纯自研代码 |
| **原版 APK / 资源包** | **绝不分发** | Square Enix 版权；必须由用户自备 |

### 7.2 必须在 README 声明的（重要，别省）

1. **本项目不含游戏本体**。用户须自行合法获得原版 APK（2013 年国服客户端）与资源包
2. 合并器**不破解、不绕过付费**；它只是把"离线可玩所需的本地服务器与资源"装配进用户自己的客户端副本
3. **不要分发合并后的 APK**（含 Square Enix 素材，属二次分发）
4. **不要用于商业用途**
5. 与 Square Enix / 盛大**无任何关联**；遇到问题不要去找官方
6. **无任何担保**（MIT 的免责条款）
7. 收到版权方通知将立即下架

### 7.3 另一个法律相关点：`librooneyj.so`

它是**原版 native 库 + 4 个补丁**（含"扭蛋业务错误弹窗"补丁）。
- 随 Release 分发它 = 分发原版二进制的修改版
- 这与"分发完整 APK"性质相近，**不能算完全干净**

**可选更保守做法**：合并器不预制 `.so`，而是**现场对用户自己的 `.so` 打 4 个二进制补丁**。
- 优点：不分发任何原版二进制
- 代价：需要把 4 个 native 补丁实现成对 `.so` 的字节级 patch（要先把每个补丁定位成"偏移+原字节+新字节"）
- ❓ 见 §12 Q6

## 9. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 用户提供的 APK 版本不匹配 | 换入的 `classes.dex`/`.so` 不兼容 → 崩溃或黑屏 | **SHA256 白名单强校验 + 明确报错**（不匹配就拒绝，别硬来） |
| 资源包不完整（缺卡图/场景） | 引擎对缺图**零容忍** → 崩溃（历史惨痛教训） | 校验资源包**条目数与关键路径**（如 6932 项、卡图族存在）；校验失败拒绝 |
| v1 签名在 Android 14+ 被拒 | 装不上 | ❓ 需实机验证；必要时补 v2 |
| 输出 900 MB 传输/安装失败 | 用户以为工具坏了 | README 明确提示 + 工具检测磁盘空间 |
| 内存不足（低配机） | 崩溃 | 全程流式（`shutil.copyfileobj`），不整包读入 |
| 杀毒误报（PyInstaller 产物） | 用户不敢用 | README 说明 + 提供源码运行方式 + 附 SHA256 |
| 用户以为"合并器=盗版下载器" | 舆论/法律风险 | README 第 1 段就写清定位 |

## 10. 实施计划（建议分四步）

| 步骤 | 内容 | 交付 |
| --- | --- | --- |
| **S1** | `artifacts-tool/collect.py`：从当前构建产物提取 artifacts + 生成 SHA256 清单 | `artifacts/` + `manifest.json` |
| **S2** | 核心合并（CLI）：校验 → 组装 → 签名（v1）→ 输出 | 能跑通，输出可安装 |

## 12. 需要你决定的问题（❓）

### Q1. OP 动画（`op.mp4`，101.6 MB）要不要放进合并器？

- **背景**：当前修复版带的是**神经超分版** OP（480×272 → 1920×1088），101.6 MB。
  原版 OP 在用户资源包里**没有**（`assets/save` 里没有它），它原本在 APK 的 `assets/kssma-data/`。
- **选项 A**：带上（合并器 artifacts 113 MB，用户开箱即得高清 OP）
- **选项 B**：不带（artifacts 降到 ~11 MB；但合并产物**没有 OP**，或需要从别处补）
- **选项 C**：带上但要用户**额外下载**（首次运行提示）
- 我的倾向：**A**（体验完整优先）；但如果你想让 artifacts 尽量小，就 **C**。
  注：OP 缺失会导致开场黑屏/跳过，不影响游戏本体。

### Q2. 合并器用什么许可证？

- **A. MIT**（我推荐：最宽松省事）
- **B. Apache-2.0**（多了专利条款与 NOTICE）
- **C. 其他**（你指定，如 GPL-3.0 —— 但会限制别人二次分发）

### Q3. 用户拿到的是什么形态？

- **A. 单文件 exe**（PyInstaller 打包，我推荐；用户零依赖，但体积 ~20–40 MB，可能被杀毒误报）
- **B. Python 脚本 + 说明**（体积小、透明，但用户要装 Python 3.9+）
- **C. 两个都要**（exe 为主，源码可跑）
- 我的倾向：**C**（同时满足"怕麻烦"和"想审计"的两类用户）

### Q4. 签名策略？

- **A. 仅 v1，先实机验证**（实现最简单）
- **B. 直接 v1+v2+v3**（与现有修复版一致，但要多写 APK Signing Block 的实现）
- 我的倾向：**A → 验证后按需补 B**。若你希望"一次到位不折腾"，就选 **B**。

### Q5. 一致性目标是"内容等价"还是"逐字节等价"？

- **A. 内容等价**（每个条目内容一致；zip 元数据/签名可不同）—— 我推荐
- **B. 逐字节等价**（SHA256 完全相同；需要固定 mtime、条目顺序、压缩参数、签名时间戳）
- 我的倾向：**A + 提供条目级校验报告**。B 技术上可行但对用户没有额外价值。

### Q6. `librooneyj.so` 怎么处理（法律权衡）？

- **A. 预制并分发**（简单、可靠；但等于分发原版二进制的修改版）—— 我倾向
- **B. 现场给用户的 `.so` 打 4 个字节级补丁**（不分发原版二进制，法律上更干净；但要先把 4 个补丁反解成"偏移+原字节+新字节"，且要处理版本差异）
- 你怎么看？如果你更在意"干净"，我走 B（会增加约半天工作量）。

### Q7. `AndroidManifest.xml` 怎么处理？

- **A. 预制我们的版本**（apktool 重编码后的；简单，但 manifest 变了会让"内容等价"多一条例外）
- **B. 现场在用户原版 manifest 上做二进制字符串替换**（只改 GM 组件名那处；更干净、更小，但需要自己写 AXML 字符串池改写——项目里已有该方法论）
- 我的倾向：**A**（先跑通），若你要求极致干净再换 **B**。
