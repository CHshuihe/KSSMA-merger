## 6. 一致性验证方法

### 6.1 条目级核对（**已实测通过**）

合并器内置了对拍工具：

```python
from merger.report import compare_with_reference
same, diff, only_new, only_ref = compare_with_reference("合并产物.apk", "官方修复版.apk")
```

**实测结果（2026-10-04，M23 修正后）**：

| 指标 | 结果 |
| --- | --- |
| 条目内容相同 | **7760** |
| 条目内容不同 | **0** |
| 仅合并产物有 | **0** |
| 仅官方修复版有 | **0** |
| 压缩方式 | 产物 STORED 7759 / DEFLATED 1（仅 manifest）；官方 STORED 7759 / DEFLATED 4 |
| 体积 | 产物 901.5 MB / 官方 901.3 MB |
| 耗时 | **5.3 秒** |
| 可复现性 | 两次构建 **逐字节一致**（sha256 `70bcd135…`） |

> **结论**：合并产物与官方修复版**逐条目字节一致**（含 `assets/save/appdata/*`）。

**为什么 `assets/save/appdata/*` 必须带上（M23 修正）**：

早期版本曾**故意跳过**这两个文件，理由是"2014 全零旧存档会让客户端删卡表"。这个判断是**反的**：

- 资源包里这份 `save_appdata` **不是全零**（2849 字节 / 118 个非零字节），与官方修复版同一份
  （`sha256 59c228bf…`）；**全零的是设备上被客户端改写后的那份**。
- 客户端启动时若读到**全零或缺失**的 appdata，会在 `GLRenderer.nativeInitialize` 里
  删掉 `save/database/master_card`，且**不会**去 `/connect/app/masterdata/card/update` 重下
  （实测：客户端整个会话只请求 9 条路由，masterdata 零命中）。
- 引擎卡表因此为空 → 图鉴 `_CardCollection::setupCardTable → createFaceCard →
  _Card::getCountryId()` 对 NULL 取成员（`fault addr 0x8`）→ SIGSEGV。
- `KssmaBoot.healZeroSaveAppdata()` 的自愈依赖 **asset** `save/appdata/save_appdata`：
  包里没有它时只能打 `save_appdata heal skipped: asset missing`，无从修复。

**M23 修法**：`apkbuild.py` 不再跳过 `appdata/`；`validate.py` 增加硬门禁——
资源包缺 `appdata/save_appdata` 或它全零时**直接拒绝打包**。

### 6.2 二进制补丁自查

```
# 从原版 .so 重放补丁，应与修正后逐字节一致
python merger/src/tools/make-binary-patch.py verify \
    librooneyj.orig.so librooneyj.patched.so patch-librooneyj.json

# 或直接应用到文件（带三重校验、幂等）
python merger/src/tools/apply-binary-patch.py \
    merger/patches/librooneyj.so.patch.json <目标.so>
```

**已实测的三个场景**：

| 场景 | 结果 |
| --- | --- |
| 干净原版 `.so` | `e0c4b63b…` → `e410d845…`（56 区间 / 442 字节）✓ |
| 重复应用 | 幂等跳过 ✓ |
| 被篡改的文件 | 拒绝且**不改动** ✓ |

### 6.3 补丁描述格式

```json
{
  "format": "kssma-binary-patch/1",
  "label": "librooneyj native patches（含 rarity7 详情面板修复）",
  "from_sha256": "e0c4b63b…",
  "to_sha256":   "e410d845…",
  "size": 4476928,
  "region_count": 56,
  "changed_bytes": 442,
  "regions": [ { "offset": 1850280, "before": "d9a8fef7d5f8", "after": "24f2fab900bf" }, … ]
}
```

**安全保证**：
1. 应用前核对整文件 `from_sha256`
2. **逐区间**核对 `before` 字节 —— 任一不符立即中止，绝不硬打
3. 应用后核对整文件 `to_sha256`

### 7.4 已知的**既有**问题（非合并器引入）

**教程路径会让客户端主动退出**（`AndroidRuntime: VM exiting with result code 0`）。

- 触发条件：**全新账号**（存档 `tutorial.step = 100`）走教程流程
- 现象：`login` 返回教程场景后，客户端立刻 `System.exit(0)`，屏幕上先显示"无法连接服务器"
- **对照实验结论**：用**官方修复版 APK** 走同样流程，**行为完全一致**
  （同样 `login tutorial step=100 -> enter tutorial` → 同样 VM exiting）
  → **这是既有的教程实现缺陷，与合并器无关**，合并产物与官方版行为等价
- 绕开方式：存档里 `tutorial.step = -1`（标记教程已完成）即直接进主城
- 待查：登录应答里教程场景的报文形状（`next_scene=100`）是否是客户端退出的原因

### 7.3 已知的设计取舍

| 取舍 | 原因 |
| --- | --- |
| **必须**带上 `assets/save/appdata/*` | 缺它/全零会让客户端删掉卡表 → 图鉴等卡牌页 native 崩溃（M23，见 §6.1） |
| 输出几乎不压缩（STORED） | 与公开修复版一致；引擎按偏移直读资源，省解压 |
| 不做"逐字节可复现" | ~~需固定签名时间戳与 zip 元数据~~ 实测两次构建已逐字节一致（M23 复核，sha256 `70bcd135…`） |
