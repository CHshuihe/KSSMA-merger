### ① 战斗改为原版**行制回合模型**（本版最大的行为变更）

- **每回合我方先出一行（最多 3 张，左→右依次出手），之后才是敌方（妖精）回合。**
  这是原版的回合模型；此前是"全部卡组每轮出手、打到一方 HP 归零"。
- 依据是客户端自带的真服务器抓包样例 `assets/bundle/local_battle_player.xml`
  与 `Kakusansei-Million-Arthur-Reborn`（reborn）的实机校正口径（见 `notes/M34-*` §0 的基准表）。

### ② 卡组 **4 行 × 3 列** 固定轮换

- 12 槽 = 4 行 × 3 列，轮换 **ABC → DEF → GHI → JKL → 循环**；12 卡满编时 **8 回合每行出手两次**。
- **按槽位分行**（槽 1-3 / 4-6 / 7-9 / 10-12）：一行摆几张就出几张、判定几张，
  **不把后面行的卡补上来凑三张**；**空行跳过**，轮完自动回到第一行。
  （只摆槽 1/4/7 时，每回合只出 1 张，而不是被切成"1 行 3 张"。）

### ③ 技能判定：每回合最多 1 个生效、每卡每场只生效一次

- 每回合**从左到右最多 1 个技能生效**（先到先得，命中后本回合后面的卡不再判定）。
- **每张卡的技能一场战斗只生效一次**；已生效过的卡再次出场（第 5 回合回到 ABC）不再判定。
- 三个都没出 → 直接普攻。

### ④ 必杀 EX 满后**下一回合开场**释放

- EX 充能满后**下一回合开场立刻自动释放**；**释放后当回合卡牌照常行动**。
- 进战斗时 EX 已满仍压到 **99**（M33 的 V6-1 防"首动作必杀卡死动作队列"保底**保留**）。

### ⑤ 打满 8 回合未击杀 = 战斗失败

- **回合预算 = `battle.turns = 8`**（原版上限）。打满 8 回合双方存活 = **未击杀 → 判玩家负**，
  **妖精带剩余血量留在场上**（可再战或等协战），**不再伪造补刀动作**、不再按剩余 HP 判胜。

### ⑥ 伤害上报原始值，波动 ±20%

- 伤害上报**原始值**（过杀不截断，内部 HP 下限 0）；随机波动范围调成与原版一致
  （**±20%**，即 80%~120%；此前 ±10% 覆盖不住样例的 0.83/1.20 两端）。

### ⑦ EX 恢复调回原版 +5/回合

- `battle.ex_gauge_per_turn` **34 → 5**（原版每轮 +5），必杀节奏回归原版"两三轮一战"；
  旧的 34 是 200 轮模型下为 2~3 轮一发调出来的参数。
- 「攻击回合数越多」系技能按**原版 8 回合预算**插值（步数 = `rounds − 1`，撤销旧的 cap 4）。

### ⑧ 修攻击动画"错误上浮"

- **现象**：发动技能的卡**不**上浮、没技能的卡**反而**上浮。
- **根因**（`.so` 反汇编实锤）：`attack_type` 是客户端**攻击动画分支开关**（`>1` 与 `≤1`
  两条编排），而原版真服务器样例 6 张卡**全部 `attack_type=1`**、Go 参考也恒 1 ——
  **wire 值不是卡面动画类型**。M29 的 V4-4 无抓包依据地把它改发卡面真值 1/2/3，
  导致约 62% 普攻走了"强调/上浮"分支（旧 12 卡全出手模型下看不出来，
  行制后每回合 3 张立刻露馅）。
- **修法**：`attack_type` **恢复恒 1**（撤销 V4-4），`masterAttackType()` 删除；
  自检断言 `battle attack_type real value` → `battle attack_type constant 1`。

### ⑨ 切尔莉**十连** + 扭蛋选择页六行重排 + 按钮文字居中

- **十连档**：`gacha.json` 新增**产品 6「切尔莉10连扭蛋」**（**2000 友情点一次抽 10 张**，
  与产品 5 共享同一份狗粮池，`drawCount=10`、`behavior="6,0,0,0"`）；
  买路径零改动（余额/持卡空间预检、不足弹窗对 `drawCount=10` 自动生效）。
- **六行重排**：选择页 = 友情横幅 + 五个按钮行，行距 40→32（`y=96..224`），
  末行底 ≈256 ≤ `scrollHeight` 280 —— 实测**该场景没有可用滚动**，加行只能挤进一屏。
- **按钮文字居中**：① 十连按钮首轮**没有文字**——按钮文字不是按钮自带的，
  而是**独立文本条**（`actionId=0` 的 `textdata`）叠加，首轮建行时漏建 → 已补文字条；
  ② 其余按钮文字是**左对齐残留**（x 恒 140）→ 按反汇编标定的按钮中线 x≈160
  逐条算居中 x、y 改行 +7 垂直居中（`{cost}` 占位符**保留**，GM 改价后标签同步）。
- **附带**：`textdata` 的 `color` 是**死键**（message 只认 `text`/`size`，恒白渲染）；
  `anchor` 语义未证，本轮未用。

该版把 `bugrecode261003.txt` 的 **bug v6（8 条）**处理完毕：**6 条修掉、1 条纯调查答复、

### v6-1 · 开局必杀让动作队列卡死（**本轮唯一的深坑**）

- **现象**：存档 EX 满时进妖精战，**战斗第一个动作就是必杀** → 切绘播完后动作队列
  **有概率**不再推进：场上卡牌消失、敌方血条冻结在初值，约 40 秒后客户端自行退回妖精列表。
  **同一配置另一场却能正常播完**（竞态，非确定性）。附带症状：低血量时场上只剩第一张卡。
- **根因**：必杀作为**战斗第一个动作**时，客户端必杀演出任务链有概率卡死整个动作队列。
  原版 SUPER 槽每轮 +5 且**不跨战斗继承**，必杀最早也要第 20 轮，"必杀打头阵"在真服务器上
  根本不存在（客户端自带样例开局 `<ex>95</ex>`，接近满但不满）。
  本服服务器**跨战斗持久化 EX + 每轮 34 + 连携加成**三因素叠加，把必杀推到了第一动作才踩中。
- **修法**：服务端保底——**开局 EX 封顶 `superMax-1`**，必杀最早**第 2 轮开场**触发。
- **实测**：修复前日志 `actions=[1:[EX!,22,100,…]]`（必杀打头）；
  修复后 `actions=[1:[22,100,130,…13 张卡] 2:[EX!]]`（`won=true rounds=2`），
  第 1 轮卡牌伤害数字正常跳出、第 2 轮开场必杀正常播完、正常结算。
- ⚠️ **行为变更：没有"开局大招"了。** EX 满进战斗时下发展为 **99**。
  想恢复"开局大招"需要走 dex 字节码层给必杀演出任务补"队列首动作"分支——引擎层高风险改动，未做。

### v6-4 · 妖精等级成长（**M33·最大的功能变化**）

- **现象**：妖精**永远 1 级**（等级写死在池配置里，没有递增机制）。
- **修法**：存档新增 `battle.fairy.levels{bossId: 下次等级}`，按级线性缩放 —
  **HP +15% / 级、攻击 +5% / 级、奖励 +10% / 级**，**30 级封顶**；
  比例与上限**全部可在 `runtime-config.json` 的 `fairyEncounter` 段调整**
  （`levelHpPct` / `levelAttackPct` / `levelRewardPct` / `maxFairyLevel`）。
  胜利后 +1；**普通/觉醒按各自 `bossId` 独立计档**。
- **实测**：连打 6 场 → `levels {30024:1→5, 30025:1→3}`；战斗 XML `<lv>2</lv>` +
  hp `19044`（=16560×115%）+ power `1376`（=1311×105%）。

### v6-2 · 觉醒妖精改为概率生成

- **现象**：觉醒妖精**直接出现在遭遇列表**里（`rareFlg=1` 的条目直接进池抽，weight 8 vs 100）。
- **修法**：池抽选**排除 `rareFlg=1`**；改为**击败普通妖精后掷骰 `awakenChancePercent`**
  （默认 **30**，可配）生成觉醒版。配对约定：觉醒 `bossId` = 普通 `id + 1`（146 条数据全部成立）。
- **行为变更**：妖精**不再直接刷觉醒**，而是打完普通妖精有 30% 概率冒出来。

### v6-5 · GM 可重置妖精等级

### v6-7 · 卡牌仓库扩建道具

- **现象**：仓库到上限后没有扩容手段（上限链路 `cards.max` → `<max_card_num>` 本来就是通的，只是没上架）。

## 更早（2026-10-06 · M27–M32）**bug v4/v5 全清 + 一条没人报过的隐藏硬墙**

该版把 `bugrecode261003.txt` 的 **bug v4（5 条）与 v5（2 条）全部关闭**，并额外修掉一条
**从没人报过**的问题（**Lv41 等级墙**）。以下六节**从新到旧**排列，完整根因与实机证据见

### M32 · 战斗报文卫生（性质：**报文卫生**，不改战斗形态）

- **现象**：17/17 条**必杀**动作带 `<attack_card>null</attack_card>` 三兄弟；30/30 场**没有 `attack_ex`**
  （EX / 必杀槽逐轮不动）；3 卡卡组下发 `<maxhp>8551</maxhp>` 而同侧卡列表之和只有 8550（**差 1**）。
- **根因**：`FairyXml.appendBattleActions` 对**所有非 turn 动作**无条件写那三个标签，而必杀动作的
  map 里根本没有 `attack_card`；服务端只改内存 `playerEx`、**从不产出动作**；HP 累加器初值写成了 `1`。
- **修法**：三标签改为"真有 `attack_card` 才写"；每轮末尾补一对 `attack_ex` 动作
  （敌方 0 / 玩家本回合增量，与官方抓包样例和 Go 参考同形）；累加器初值改 `0`。
- **影响**：三条里**只有 `attack_ex` 有演出可见性**（客户端 `toInt` 把 `null` 当 0）。
  12 场实测：`null` 标签 **0**、`attack_ex` 覆盖 **53/53 = 100%**、`maxhp` 与卡列表之和**严格相等**。
  战斗形态**未改**：仍是打到一方 HP 归零，`battle.turns` **有意**仍不用于封顶。

### M31 · Lv41 等级墙 + PvP 敌方阵营 + 加点统一

- **现象**：等级**卡在 Lv41**——经验照涨，但 `<next_exp>` / `<percentage>` / `is_limit` 恒 0，
  玩家观感就是"经验条坏了"（且客户端不会提示满级）。
- **根因**：`levelRow` 要求**逐行精确命中**，而等级表只有 **118 行 / Lv1..199**，
  **缺 81 个等级，首个缺口正是 Lv41**。
  （早期笔记里"实际卡在 Lv200"的结论**是错的**——真值 Lv41；而且表里**根本没有 Lv200 行**。）
- **修法**：精确命中优先 → 缺口**向下取"小于目标的最大行"**（**不编造**缺失等级的数值）→
  超出表尾按最后一段差分**线性外推**；`maxLevel` 仍保持 350；返回行的 `level` 一律改写为目标等级。
- **影响**：Lv41 之后恢复正常升级（设备端到端：Lv40→41、Lv41→42 都拿到正确 `next_exp`）。
  ⚠️ **Lv200~350 的阈值是我们外推的，不是考证值**；缺口区间"向下取最近行"会让升级**比真实值更快**。
  这两段数值不可信，日后拿到权威表直接替换 `player-level-exp-table.json` 即可，代码不用再改。
- 同轮另修两处：PvP **敌方** `<type>` 原本发的是**对手 userId**（客户端拿它当模型号，于是对手用的是自己的立绘）
  → 改发对手阵营 1..3；妖精战升级加点与探索路径统一（50 级前 +3 / 之后 +2），`percentage` 钳到 100。

### M29 · 妖精遭遇池 + 战斗技能条件引擎

- **现象**：妖精**永远只有小龙女**；战斗技能"条件不对也能触发、而且反复触发"。
- **根因**：妖精遭遇是**单对象写死**（30024 小龙女），代码里根本没有"出哪只"的抽选；
  技能是"每轮每卡 30% 掷骰、type 2/12 回血、**其余一律攻击×2**"，描述里的条件全被无视。
- **修法**：`runtime-config` 新增 **`fairyEncounterPool`（146 条** = 76 base + 70 觉醒稀有位，
  按区域分档 + 加权抽选），支持**多只并存**讨伐（`maxActiveRaids=3`，过期妖精自动解锁）；
  技能改为按 `skill_description` 的**规则句式**解析（无条件每卡每场 1 次 / 第一轮 / HP≤X% /
  等级 MAX / 对手是妖精或指定名 / 缩放族），**"战斗胜利后"系移出战斗循环**改胜利后结算。
- **影响**：实机三次探索依次遭遇**不同**妖精，技能名横幅真的弹出并造成伤害；`attack_type` 改发卡面真值。

### M28 · 限界突破（此前是**死功能**）

- **现象**：限界突破**完全没反应**，也不涨上限。
- **根因**：实现在 `settleEvolve` 的同卡分支里，而客户端进化页对无配方卡**全部禁用**
  （有配方的卡素材又被自动锁定）→ **UI 没有任何路径能触达**；即使触达，`limit_over` 也只加计数器，
  上限/属性读的是别的字段。
- **修法**：**强化合成喂同 `master_card_id` 的素材 = 每张 1 次突破**（同卡走突破、异卡照常折经验的
  混合素材）；上限 `max_lv(+holo) + min(limitOver, limitBreakMax) × limitBreakLevelGain`（2 / 4，可配）；
  属性沿 base→lvmax 斜率**线性外推**（按新上限重新插值会让突破瞬间同级属性**回退**）；
  计费改用与客户端预览同一公式，消掉"弹窗 240 实扣 3000"的显示错位。
- **影响**：实机卡面显示 `Lv. 1 / 24` + "界限突破 还有 1 次"；自检 367 绿。

### M27 · 闪卡 + 切尔莉

- **现象**：扭蛋**永远不出闪卡**；卡池里**没有切尔莉**（390 / 391 / 392 / 404）。
- **根因**：闪卡在数据层齐全（`max_lv_holo`、holo 属性列、`thumbnail_*_horo` 资源都在），
  **唯一缺口是发卡路径 `holography` 恒写 0**；切尔莉 4 张在卡表里是 `data_type=2`（NPC/素材命名空间），
  被扭蛋护栏 `data_type≠1 拒发` 误伤。
- **修法**：新增 `gacha.holoRatePercent`（缺省 0 = 与历史行为一致，**交付值 5**）逐抽掷骰，
  扭蛋与妖精奖励共用同一概率；卡表 **4 处等长改写 `data_type` 2→1**，四产品池按
  "同产品同稀有度众数权重"收录，并给它们专用饲料经验（`compound.materialExpOverride`）。
- **连带关键修复**：`KssmaBoot.forceCopyAssetFile` 由"长度相等即跳过"改为**逐字节比对**——
  否则本次这种**等长改写永远同步不到老装机**（配置类资产不同步第 4 次复发）。
- **影响**：实机抽出**闪卡切尔莉**（holo 边框、售价 ×2、喂养经验 ×2）；自检 355 绿。

## 更早修复（2026-10-05 · M26）**强烈建议更新：修掉"打完妖精必闪退"**

**现象**：从「菜单 → 妖精选择 → 打妖精」这条路径打完妖精，客户端**必定闪退**
（`SIGSEGV / fault addr 0x0`）。**从探索场景里打不会**——所以之前一直没被发现。

**根因**：客户端的探索场景 BGM 组件（`_ExpBgmComponent::playBgm`）把属性 `bgmName` 拼成
`"bgm_" + bgmName` 再去播放；这个属性绑定布局图纸里的模型字段，而模型字段**只由应答里
顶层的 `<get_floor><bgm>` 填充**。妖精战应答的 `result_scene` 复用**探索主场景**，却没有带
`<get_floor>` ⇒ 新场景的 BGM 名为空 ⇒ 拼出空字符串 ⇒ 解引用空指针 ⇒ **必崩**。

**修法**：凡是把结果场景指向探索场景的应答，都补上顶层 `<get_floor>` 块
（妖精战 4420 / 守护者战 4410 / 续探索），`<bgm>` 取该区域的 BGM（缺省 `sarch1`）。
顺带把"区域 bgm 配了空串"也纳入兜底，保证**永不为空**。

**实测**：冷启 → 不进探索 → 菜单 → 妖精选择 → 打 → **新增崩溃 0 次**、进程全程稳定、
客户端日志确认真的以 `bgm_sarch1` 播放成功；原先同路径连崩 3 次（`tombstone_29/30/31`）。

## 更早新功能（2026-10-05 · M25）**战斗 combo 真实生效**

以前战斗里的"连携（combo）"是**空壳**：服务器只发一条硬编码的「信条奖励」，
且 `combo_hp_player` / `combo_ex_player` 都是 **0** —— 界面弹一下、数值毫无变化。
`master_combo` 里的 **196 条真实 combo 定义从来没有被读过**。

现在：

- **按真实定义匹配**：解析 `master_combo`（196 条），按客户端同款算法（攻击类型 / 阵营 /
  指定卡 / 卡组张数 / 性别 / 系列，同组取 `priority` 最小）判定你**当前卡组**命中哪些 combo；
- **下发真实 combo**：每条命中各发一条 `<battle_action_list>`，`combo_id` / `combo_name` /
  参战卡列表 / HP / EX 全为真实值；
- **加成真的进数值**：HP / 攻击% / EX / 技能率 / 必杀% 五个频道（幅度在
  `kssma-data/server/runtime-config.json` 的 `combo` 段里，可自行调平衡）；
- 妖精战 / 区域守护者 / 人机对战三处共用；战斗日志会打印 `combos=… hp+… ex+…` 便于确认。

> 组卡界面里的 combo 显示本来就是**客户端本地**功能（不需要服务器），本版没有改动它。

**已实测**：卡组 `124,8,9,40,83,108` → 命中 `Rush COMBO` + `Princess COMBO`，
玩家 HP 由面板 8501 变为 **10201**、开局 SUPER EX **44**；换成不匹配的卡组则 0 条 combo、数值不变。

## 更早修复（2026-10-05 · M24）**建议务必更新**

**7★ 卡的卡片详情整块空白**（连横幅与 STATUS/SKILL/CHARACTER 都没有）。原因不在数据
（482 条卡表里 7★ 的 19 张文案全齐），而在客户端两处与 `rarity` 相关的代码：

- `_AnmCardDetail::drawHead` 把 **`rarity + 1` 当图集帧号** → 7★ 得帧 8，而这份 2013 客户端
  只有 1..6 档（帧 2..7）；

  → `fp = 0` → 面板什么都不画。

**修法**（`.so` 两个区间，共 25 字节）：帧号 clamp 到 7 + rarity≥7 的默认变体指向 6★ 那档。
`.so` 指纹随之从 `36a4826b…` 变为 **`235e2cd1…`**（区间 54 → 56）。

- 效果：7★ 详情显示 **`SUPER RARE +`** 横幅 + **完整技能与介绍**，左侧卡面仍是 **7 颗星**；
  右侧星条不显示（该档美术不存在）。
- 回归：1★~6★ 帧号逐位不变。
- **UR 说明**：这份 2013 客户端里详情横幅**没有 UR 那一档**（实测把变体改成第 7 档会连横幅都没有），
  `1200_card_detail`/`carddetails` 是引擎自解密封装、资源包（140330, 2014-03）也没带 UR 帧
  → **真 UR 需要更晚期的客户端资源包**，当前只能显示到 `SUPER RARE +`。

## 已知限制（重要）

**输出目录必须在程序文件夹那一带。** 部分安全软件会限制本程序只能在自己所在
位置的目录树内写文件（本程序要生成约 900 MB 的 APK），写到别处会报
`Permission denied`，**即使那些目录权限完全正常**。

- ✅ 程序文件夹内 / 其子目录 / 其上级目录
- ❌ 其它盘或无关目录（如 `D:\Engine`）

想换位置 → **把整个程序文件夹搬过去再运行**。程序也会在开始合并前预检，
并在报错时主动提议切到可用目录。

## 常见问题

**Q：提示「输出目录不可用 / 写入被拒绝」？**
见上面「已知限制」。把整个程序文件夹搬到你想输出的位置，或恢复默认输出目录。

**Q：杀毒软件报警？**
未签名的 PyInstaller 打包程序常被误报。可从源码运行，或自行校验 SHA256。

**Q：命令行模式没有输出？**
GUI 版 exe 是窗口程序，标准输出不出现在终端里。要在终端看输出请用源码运行：
`python src/main.py --apk <apk> --res <zip> --out <dir>`

**Q：为什么输出 APK 有 900 MB？**
原版客户端 + 完整资源包（全部卡图、立绘、场景、音效、OP）就是这体量。
